# CR2SE Messaging

CR2SE Messaging is a paid service for retaining a message addressed to one
CR2SE identity until that identity recovers it or an agreed retention period
ends. The **sender** is the identity that creates and stores the message. The
**recipient** is the identity named by the sender as authorized to receive it.
**Recovery** is the successful return of the complete stored message to an
authenticated recipient.

The sender selects the recipient, the message bytes, and the retention period.
A provider retains the message and reveals it only to a peer that proves
control of the recipient identity. The sender may later ask whether recovery
occurred. If one copy was recovered, the sender may remove copies held by other
providers and may receive provider-issued credits in return for releasing the
unused retention commitment.

The message bytes may be plaintext or ciphertext. Encryption for the recipient
before upload is strongly recommended for private messages, but it is not a
condition of the service. A provider can route and retain encrypted bytes
without being able to decrypt them.

Common terms such as **identity**, **service requester**, **service provider**,
**offering**, **credit issuer**, and **check** are defined in the
[CR2SE Glossary](./Glossary.md). Common invocation and charging rules are
defined in [Services](./Services.md). Identity proof is defined in
[Identity](./Identity.md), cryptographic algorithms are defined in
[Encryption](./Encryption.md), and credit accounting is defined in
[Ledger](./Ledger.md).

---

## 1. Version 1 service

The version 1 Messaging service is identified by:

```text
service:        cr2se.messaging
serviceVersion: 1
pricing model:  cr2se.messaging.v1
```

It supports these operations:

```text
store       retain one signed message for one recipient
discover    list pending message metadata for the authenticated recipient
recover     return one pending message to the authenticated recipient
status      tell the authenticated sender whether one placement was recovered
renew       extend the retention period of one placement
remove      end one pending placement and apply an agreed credit release
```

Each operation acts on one provider. Storing the same message at four providers
creates four independent service agreements. Messaging version 1 does not
replicate a message automatically and does not notify the other providers when
one copy is recovered.

All sizes are measured in bytes. All durations are whole seconds. All protocol
integers use the ranges of their declared types; fixed-width integer arithmetic
must never wrap.

---

## 2. Messages and placements

A **message** is a signed association between metadata and one immutable byte
sequence called the **payload**. Its metadata identifies the sender, recipient,
creation time, payload representation, payload size, and payload hash.

A **message ID** is a 32-byte value generated by the sender with a
cryptographically secure random number generator. It identifies one message.
The sender uses the same message ID and exactly the same signed message when
placing redundant copies at several providers.

A **placement** is one provider's accepted agreement to retain one message. A
**placement ID** is a 32-byte, cryptographically random value generated by that
provider. It is unique among placements at that provider and identifies that
agreement in later operations.

The **acceptance time** is the provider's Unix time when it durably accepts a
placement. It is represented by `acceptedAt`. The **expiration time** is the
acceptance time plus the agreed retention duration. It is represented by
`expiresAt`.

The distinction is:

```text
one signed message
        |
        +-- placement at Carol, placement ID C
        +-- placement at David, placement ID D
        +-- placement at Ellen, placement ID E
        +-- placement at Fabian, placement ID F
```

The shared message ID lets a recipient recognize these as copies. Each
placement ID lets the sender or recipient address one provider's copy. Neither
identifier is an encryption key, password, or bearer authorization token.

An accepted placement records at least:

```text
placement ID
complete signed message and payload
sender identity
recipient identity
provider identity
offering ID and version
acceptance time
expiration time
cumulative store and renewal prices, and credit issuer
placement state
```

The provider may choose any internal database, file, object-store, or other
representation that preserves these observable values and behaviors.

### Placement states

A placement has these conceptual states:

```text
receiving -> pending -> recovered
                  |\-> removed
                  \-> expired
```

`receiving` is an incomplete upload and creates no retention obligation.
`pending` means that the complete message was durably accepted and may be
discovered and recovered by the recipient. `recovered` means that the provider
successfully completed the first recovery operation authorized by the
recipient. `removed` means that the sender ended a pending placement early.
`expired` means that its expiration time was reached while it was pending.

The provider must retain the complete payload while a placement is pending. It
must retain the placement metadata, recovery record, and cached recovery output
until expiration after a placement becomes recovered. The cached output still
contains the payload, but it is available only to an idempotent retry of the
successful recovery defined in section 10.

A removed or expired placement has no further retention obligation. The
provider may keep a local tombstone for replay prevention, but version 1 does
not require status queries to succeed after removal or expiration.

## 3. Message metadata

The sender supplies these logical metadata fields:

```text
messageId:       bytes, exactly 32 bytes
senderId:        bytes, exactly 32 bytes
recipientId:     bytes, exactly 32 bytes
senderCreatedAt: uint64 Unix seconds
payloadEncoding: string
payloadSize:     uint64
payloadHash:     bytes, exactly 32 bytes
```

`senderCreatedAt` is the sender's claimed creation time. Unix time is the number
of elapsed seconds since 1970-01-01T00:00:00Z, excluding leap seconds. A
provider may reject implausible values by local policy, but the field is not a
trusted clock reading.

`payloadEncoding` is exactly one of:

```text
opaque
    The service assigns no encryption or text meaning to the payload.

cr2se.identity-encrypted.v1
    The payload uses the encrypted representation defined in section 6.
```

`opaque` does not mean plaintext. It can contain plaintext, an application
format, or ciphertext produced by another protocol. Only the second value
claims the interoperable CR2SE encryption format from this document.

`payloadSize` is the exact number of payload bytes and must be at least one.
`payloadHash` is:

```text
SHA-256(payload)
```

Message metadata is visible to every placement provider. Encryption protects
the payload, not the sender ID, recipient ID, size, timing, provider selection,
or access pattern.

## 4. Sender signature

Every message is signed, including a message whose payload is not encrypted.
This lets the recipient verify the sender independently of the storage
provider.

Unsigned integer fields in signing inputs are encoded as eight-byte unsigned
big-endian integers. IDs and hashes are their exact 32 bytes. A string constant
means its exact ASCII bytes without a terminating zero byte.

`payloadEncodingCode` is one byte:

```text
0x00    opaque
0x01    cr2se.identity-encrypted.v1
```

The **message signing bytes** are exactly:

```text
ASCII("CR2SE-MESSAGE-V1")
|| messageId
|| senderId
|| recipientId
|| uint64_be(senderCreatedAt)
|| payloadEncodingCode
|| uint64_be(payloadSize)
|| payloadHash
|| payload
```

`senderSignature` is the 64-byte Ed25519 signature over those bytes.
`senderPublicKey` is the sender's 32-byte Ed25519 public key.

Before accepting a store, the provider must:

1. derive an identity ID from `senderPublicKey` and require it to equal
   `senderId`;
2. require `senderId` to equal the authenticated service requester identity;
3. hash the received payload and require the size and hash to match;
4. verify `senderSignature` over the exact message signing bytes.

The recipient repeats the public-key derivation, hash comparison, and signature
verification after recovery. Provider metadata alone is not proof that the
message came from the named sender.

The signature authenticates the exact stored representation. When the payload
is encrypted, the signature covers the ciphertext rather than the plaintext.
Successful decryption separately authenticates the plaintext and its bound
metadata.

---

## 5. Recipient authorization

Only the identity in `recipientId` may discover or recover a message. The peer
making either request must prove control of that identity using the CR2SE
identity authentication mechanism.

Only the identity in `senderId` may query status, renew, remove, or check a
placement. It must likewise prove control of that identity.

Knowledge of a message ID, placement ID, payload hash, signature, or public key
is not authorization. A request through a new connection or a different node
using the same identity remains authorized after successful identity proof.

An unauthorized response must not reveal whether matching messages or
placements exist. Providers must rate-limit failed identity proof, discovery,
and identifier probing.

## 6. Recommended encrypted payload

The sender should encrypt a private payload before invoking `store`. It first
obtains the recipient's persistent X25519 public key and its Ed25519 binding
signature as defined in [Encryption](./Encryption.md).

### Board encryption-key field

A version 1 Board may publish its identity's encryption material in this
optional top-level field:

```json
{
  "identityEncryption": {
    "version": 1,
    "identityPublicKey": "BASE32_ED25519_PUBLIC_KEY",
    "x25519PublicKey": "BASE32_X25519_PUBLIC_KEY",
    "bindingSignature": "BASE32_ED25519_BINDING_SIGNATURE"
  }
}
```

Each string uses the uppercase RFC 4648 Base32 alphabet without padding. A
decoder may accept lowercase, but it must reject whitespace, padding, invalid
characters, and nonzero unused trailing bits. `identityPublicKey` and
`x25519PublicKey` each decode to exactly 32 bytes. `bindingSignature` decodes to
exactly 64 bytes.

The field belongs to the Board publisher. A recipient-key lookup succeeds only
when:

1. the CR2SE ID derived from `identityPublicKey` equals the expected Board
   publisher ID;
2. `bindingSignature` verifies with `identityPublicKey` over the encryption-key
   binding bytes defined in `Encryption.md`;
3. the decoded X25519 key passes the cryptographic implementation's public-key
   validation.

An invalid optional field makes that key unusable; it does not make unrelated
Board offerings invalid. A Messaging client should prefer this Board field. It
may obtain the same three values through another channel, but it must perform
the same identity and binding checks. Merely finding an unverified public key
on a Board is insufficient. Omitting `identityEncryption` means that senders
cannot use this lookup path; it does not prevent opaque Messaging payloads.

The following format makes encrypted Messaging payloads interoperable rather
than leaving the Encryption document's conceptual encrypted object to a
language-specific serialization.

### Encryption metadata bytes

The **encryption metadata bytes** are exactly:

```text
ASCII("CR2SE-MESSAGE-ENCRYPTION-METADATA-V1")
|| messageId
|| senderId
|| recipientId
|| uint64_be(senderCreatedAt)
```

These bytes are not secret. They bind the ciphertext to the visible message
metadata.

### Key derivation and encryption

The sender generates a new ephemeral X25519 key pair and a new random 24-byte
nonce for each message. It calculates:

```text
sharedSecret = X25519(
    ephemeralPrivateKey,
    recipientEncryptionPublicKey
)

salt = SHA-256(encryptionMetadataBytes)

messageKey = HKDF-SHA-256(
    inputKeyMaterial = sharedSecret,
    salt = salt,
    info = ASCII("CR2SE-MESSAGE-PAYLOAD-KEY-V1"),
    outputLength = 32
)

ciphertext = XChaCha20-Poly1305-Encrypt(
    key = messageKey,
    nonce = nonce,
    plaintext = applicationMessageBytes,
    authenticatedData = encryptionMetadataBytes
)
```

The sender must reject an invalid X25519 shared result as required by the
Encryption specification.

The stored payload is exactly:

```text
0x01
|| recipientEncryptionPublicKey       32 bytes
|| ephemeralPublicKey                 32 bytes
|| nonce                              24 bytes
|| ciphertext                         remaining bytes
```

The first byte is the encrypted-payload format version. The ciphertext includes
the XChaCha20-Poly1305 authentication tag. Because the authenticated-encryption
tag is 16 bytes, an encrypted payload is at least 105 bytes and its ciphertext
portion is at least 16 bytes.

On recovery, the recipient checks the version and confirms that the embedded
recipient encryption public key is one for which it holds the corresponding
private key. It reconstructs the encryption metadata bytes, derives the same
message key, and performs authenticated decryption. A failed decryption must
not yield any accepted plaintext.

The provider does not perform these encryption or decryption steps. Encryption
is strongly recommended, but `payloadEncoding = "opaque"` remains conforming.

## 7. Pricing and Board offering

Credits are integers, while byte and byte-second rates may be smaller than one
credit per unit. Every usage factor is therefore an exact fraction:

```json
{ "numerator": 1, "denominator": 1000000 }
```

`numerator` is a `uint64`. `denominator` is a `uint64` in `1 .. 2^64-1`.
Floating-point arithmetic must not be used for protocol prices.

The pricing fields mean:

```text
minimumPrice
    Minimum price of store, recover, or renew. Range: 1 .. 2^64-1.

payloadByteUsageFactor
    One-time store charge per payload byte.

payloadByteStorageDurationFactor
    Initial retention charge per payload byte-second.

recoveryByteUsageFactor
    Recovery charge per payload byte returned.

renewalByteStorageDurationFactor
    Renewal charge per added payload byte-second.

discoverPrice
    Exact price of one successful discover operation. At least 1.

statusPrice
    Exact price of one successful status operation. At least 1.

removePrice
    Exact price of one successful remove operation. At least 1.

checkPrice
    Exact price of one successful Messaging check. At least 1.
```

The offering limits mean:

```text
maximumPayloadBytes
    Largest payload accepted by store. Range: 1 .. 2^64-1.

minimumRetentionSeconds
    Smallest initial or renewal duration. Range: 1 .. 2^64-1.

maximumRetentionSeconds
    Largest duration accepted by one store or renew operation.

maximumTotalRetentionSeconds
    Latest permitted expiration relative to the original acceptedAt.

maximumDiscoverResults
    Largest requested discovery page. Range: 1 .. 2^32-1.

checkResponseSeconds
    Maximum requester-observed time for check evidence. At least 1.
```

The duration limits must satisfy:

```text
minimumRetentionSeconds <= maximumRetentionSeconds
maximumRetentionSeconds <= maximumTotalRetentionSeconds
```

A complete offering has this shape:

```json
{
  "id": "messaging-standard",
  "service": "cr2se.messaging",
  "serviceVersion": 1,
  "description": "Retain signed messages until recipient recovery or expiration.",
  "creditIssuer": "PROVIDER_ID",
  "pricing": {
    "model": "cr2se.messaging.v1",
    "minimumPrice": 1,
    "payloadByteUsageFactor": { "numerator": 1, "denominator": 1000000 },
    "payloadByteStorageDurationFactor": { "numerator": 1, "denominator": 86400000000 },
    "recoveryByteUsageFactor": { "numerator": 1, "denominator": 1000000 },
    "renewalByteStorageDurationFactor": { "numerator": 1, "denominator": 86400000000 },
    "discoverPrice": 1,
    "statusPrice": 1,
    "removePrice": 1
  },
  "checkPrice": 1,
  "info": {
    "maximumPayloadBytes": 10000000,
    "minimumRetentionSeconds": 3600,
    "maximumRetentionSeconds": 157680000,
    "maximumTotalRetentionSeconds": 315360000,
    "maximumDiscoverResults": 100,
    "checkResponseSeconds": 30
  },
  "preconditions": [
    "cr2se.identity"
  ]
}
```

The numbers are illustrative. Every version 1 Messaging offering must contain
all shown pricing and `info` fields and the `cr2se.identity` precondition. It
must use `pricing`, not the Board's fixed `price` field. Its `creditIssuer` must
equal the provider identity that published the offering. This requirement lets
that same identity apply the early-release credits defined in section 13.

Changing an offering does not shorten an accepted placement. Each later paid
operation selects a current provider offering with the same service, version,
and pricing model. The selected current offering supplies that operation's
price and limits.

### Price formulas

Let:

```text
S = payload size in bytes
T = initial retention seconds
A = renewal seconds
M = minimumPrice
B = payloadByteUsageFactor
X = payloadByteStorageDurationFactor
R = recoveryByteUsageFactor
N = renewalByteStorageDurationFactor
```

Each factor has numerator `.n` and denominator `.d`. Prices are:

```text
storePrice = max(M, ceil(S*B.n/B.d + S*T*X.n/X.d))
recoverPrice = max(M, ceil(S*R.n/R.d))
renewPrice = max(M, ceil(S*A*N.n/N.d))
discoverPrice = advertised discoverPrice
statusPrice = advertised statusPrice
removePrice = advertised removePrice
```

The two exact rational terms of `storePrice` are added before one upward
rounding. Implementations must use arbitrary-precision integers or an
equivalent overflow-safe algorithm. An input or offering whose exact result
exceeds `uint64` is invalid.

The exact price and issuer are agreed before chargeable work or a large byte
transfer begins. Failed operations are not charged.

## 8. Store

The authenticated sender supplies:

```text
operation:        "store"
messageId:        bytes, exactly 32 bytes
senderId:         bytes, exactly 32 bytes
recipientId:      bytes, exactly 32 bytes
senderCreatedAt:  uint64 Unix seconds
payloadEncoding:  string
payloadSize:      uint64
payloadHash:      bytes, exactly 32 bytes
senderPublicKey:  bytes, exactly 32 bytes
senderSignature:  bytes, exactly 64 bytes
retentionSeconds: uint64
payload:          bytes, exactly payloadSize bytes
```

The provider validates the offering limits, calculated price, identity,
signature, size, and hash. The metadata required for validation and pricing is
exchanged before the possibly streamed payload. The provider must not report
success until the complete payload and placement record are durably committed
to storage intended to survive ordinary process restart or machine reboot.

`acceptedAt` is the provider's current Unix time in whole seconds at durable
acceptance. The provider calculates:

```text
expiresAt = acceptedAt + retentionSeconds
```

A successful output is:

```text
operation:   "store"
placementId: bytes, exactly 32 bytes
messageId:   bytes, exactly 32 bytes
acceptedAt:  uint64 Unix seconds
expiresAt:   uint64 Unix seconds
price:       uint64 credits
```

The same provider may accept the same message more than once and create
different placements. Applications should normally avoid this. A provider must
reject reuse of one placement ID and must never silently replace an existing
placement.

## 9. Discover

`discover` lets an authenticated recipient ask whether a provider has pending
messages for that identity. It returns metadata, not payload bytes.

The input is:

```text
operation:        "discover"
afterAcceptedAt:  uint64 Unix seconds, optional
afterPlacementId: bytes, exactly 32 bytes, optional
limit:            uint32
```

`limit` must be in `1 .. maximumDiscoverResults`. The two `after` fields must
either both be absent or both be present. They form an exclusive cursor.

The provider orders the recipient's pending placements by `acceptedAt`, then by
unsigned lexicographic placement-ID byte order. With no cursor it returns the
first page. With a cursor it returns entries strictly after that pair. The
provider returns at most `limit` entries.

Each entry contains:

```text
placementId
messageId
senderId
senderCreatedAt
payloadEncoding
payloadSize
payloadHash
acceptedAt
expiresAt
```

The output is:

```text
operation: "discover"
messages:  array of entries
more:      bool
price:     uint64 credits
```

`more` is true only when another matching entry existed immediately after the
last returned entry when the page was produced. An empty result is a successful
and charged discovery. It reveals nothing about messages for another identity.

A caller obtains the next page by using the last entry's `acceptedAt` and
`placementId` as the next cursor. New concurrent placements can appear in a
later query; version 1 discovery is not a frozen snapshot.

Recipients should deduplicate replicas using the pair `(senderId, messageId)`.
The same `messageId` from different senders is not the same message.
The discovery sender ID is only a provider-supplied hint. The recipient knows
the cryptographic sender only after recovering the message and validating the
sender public key and signature.

## 10. Recover

`recover` returns one complete pending message. Discovery is convenient but not
required when the recipient already knows a placement ID.

The recipient generates a random 32-byte `recoveryId`. `providerId` is the
provider's 32-byte CR2SE ID. The **recovery request
bytes** are exactly:

```text
ASCII("CR2SE-MESSAGE-RECOVERY-REQUEST-V1")
|| providerId
|| placementId
|| messageId
|| payloadHash
|| recoveryId
```

The IDs and hash are exact 32-byte values. `recipientSignature` is the
recipient's Ed25519 signature over those bytes.

The input is:

```text
operation:          "recover"
placementId:        bytes, exactly 32 bytes
messageId:          bytes, exactly 32 bytes
payloadHash:        bytes, exactly 32 bytes
recoveryId:         bytes, exactly 32 bytes
recipientPublicKey: bytes, exactly 32 bytes
recipientSignature: bytes, exactly 64 bytes
```

The provider derives the authenticated recipient ID from
`recipientPublicKey`, requires it to equal the placement's `recipientId`, and
verifies the signature. Supplying the expected message ID and hash prevents a
stale client from authorizing recovery of different bytes under a reused local
reference.

A successful output contains:

```text
operation:          "recover"
placementId
messageId
senderId
recipientId
senderCreatedAt
payloadEncoding
payloadSize
payloadHash
senderPublicKey
senderSignature
payload
recoveryId
recoveredAt
recipientPublicKey
recipientSignature
providerSignature
```

Fixed-length fields retain the lengths defined earlier. `recoveredAt` is the
provider's Unix time in whole seconds when it commits the recovery record.

The **provider recovery receipt bytes** are exactly:

```text
ASCII("CR2SE-MESSAGE-RECOVERY-RECEIPT-V1")
|| providerId
|| placementId
|| messageId
|| senderId
|| recipientId
|| payloadHash
|| recoveryId
|| uint64_be(recoveredAt)
```

`providerSignature` is the provider's 64-byte Ed25519 signature over those
bytes. Together, the two signatures show that the recipient authorized this
specific recovery request and that the provider recorded its completion. They
do not prove what a human read or understood.

The transition from pending to recovered and creation of the receipt are
atomic. At most one distinct recovery ID can succeed. To handle a lost response,
the provider must cache the complete successful output until `expiresAt` and
return that identical output without another charge when the same authenticated
recipient retries the same placement and recovery ID. A different recovery ID
after recovery fails without charge.

Such a matching retry is a retransmission of the original accepted recovery,
not a new service invocation. The original recovery price is charged at most
once.

After receiving the output, the recipient validates the payload hash and sender
signature before using the payload, and decrypts it when its encoding is the
encrypted representation.

## 11. Status

`status` lets the authenticated sender ask whether one placement is still
pending or was recovered. The input is:

```text
operation:   "status"
placementId: bytes, exactly 32 bytes
```

Every successful status output contains:

```text
operation:   "status"
placementId
messageId
senderId
recipientId
payloadHash
state:       "pending" or "recovered"
expiresAt
price
```

When `state` is `recovered`, it additionally contains:

```text
recoveryId
recoveredAt
recipientPublicKey
recipientSignature
providerSignature
price
```

The signatures and receipt fields are exactly those recorded by `recover`.
The sender should verify both signatures. A recovered status means the provider
completed a recovery authorized by the recipient identity. It cannot establish
that the recipient application persisted, displayed, or understood the
plaintext.

Status is available only before `expiresAt`. A provider may retain and answer
from older records, but that is outside the version 1 obligation.

## 12. Renew

The sender may extend a pending or recovered placement before expiration. This
extends payload retention for a pending placement and recovery-status retention
for a recovered placement.

The input is:

```text
operation:         "renew"
placementId:       bytes, exactly 32 bytes
expectedExpiresAt: uint64 Unix seconds
additionalSeconds: uint64
```

The expected expiration must equal the current expiration. The added duration
must satisfy the current offering's duration limits, and:

```text
newExpiresAt = expectedExpiresAt + additionalSeconds
newExpiresAt <= acceptedAt + maximumTotalRetentionSeconds
```

The output is:

```text
operation:         "renew"
placementId
previousExpiresAt
expiresAt
price
```

Renewal becomes effective atomically with successful output. At most one
concurrent renewal with the same expected expiration can succeed. Renewal does
not change pending or recovered state.

## 13. Remove and early-release credits

`remove` lets the authenticated sender end a pending placement early. A
recovered placement is retained as status evidence until expiration and cannot
be removed through version 1.

An **early-release credit** is a provider-issued credit returned to the sender
in exchange for ending unused retention. It is a new, service-defined ledger
adjustment, not an automatic reversal, dispute refund, or guarantee imposed by
the common Services rules.

The sender generates a random 32-byte `removalId` and supplies:

```text
operation:             "remove"
placementId:           bytes, exactly 32 bytes
removalId:             bytes, exactly 32 bytes
expectedExpiresAt:     uint64 Unix seconds
minimumReleaseCredits: uint64 credits
```

Before acceptance, the provider offers one exact `releaseCredits` amount. It
may calculate that amount from remaining time and released resources or choose
it by any local policy. The amount must satisfy:

```text
minimumReleaseCredits <= releaseCredits <= cumulative placement payments
```

`cumulative placement payments` is the sum of the prices successfully charged
for the original store and every renewal of this placement. Discover, recover,
status, remove, and check prices are not part of that sum.

The sender sees and accepts or rejects `releaseCredits`, the current
`removePrice`, and the credit issuer before removal occurs. This quote step is
required because an undisclosed amount chosen after deletion would not be an
agreement. A provider may offer zero only when `minimumReleaseCredits` is zero.

Successful removal atomically:

1. changes the placement from pending to removed;
2. ends the provider's retention and discovery obligations;
3. charges `removePrice` provider-issued credits;
4. increases the sender's recognized balance of the same provider-issued
   credits by `releaseCredits`.

The output is:

```text
operation:      "remove"
placementId
removalId
removed:        true
releaseCredits
price:          removePrice
```

The two ledger changes are recorded separately even when an implementation
shows their net effect. Neither balance update may underflow or overflow.

The provider must retain enough removal-result state to return the identical
output without applying either ledger change again when the same sender retries
the same placement and `removalId`. Another removal ID for the inactive
placement fails without charge. This idempotency is required because applying
`releaseCredits` twice would create an accounting error.

A matching retry is a retransmission of the original accepted removal, not a
new service invocation. The original remove price is charged at most once.

Removal ends logical availability. It does not promise physical erasure from
backups, journals, or storage media.

## 14. Messaging check

The Messaging check lets the sender challenge a pending placement for one
payload byte. It is available only to the authenticated sender before recovery,
removal, or expiration.

The input is:

```text
placementId: bytes, exactly 32 bytes
offset:      uint64
```

The offset must be less than `payloadSize`. The sender starts a timer after
sending the complete challenge. The provider returns:

```text
placementId
offset
value: bytes, exactly one byte
```

The sender compares `value` with the original payload byte. The outcome is:

```text
pass
    matching evidence arrived within checkResponseSeconds

fail
    non-matching evidence arrived within checkResponseSeconds

inconclusive
    no valid evidence arrived within checkResponseSeconds
```

The sender should choose an unpredictable offset using a cryptographically
secure random number generator. One passing sample proves only that one correct
byte was returned at one time. It does not prove continuous storage of the
whole message or successful delivery.

Each completed check is charged at the current offering's `checkPrice` even
when its outcome is `fail` or `inconclusive`. A check that returns no valid
check result is not charged under the common check rules.

## 15. Time, concurrency, and failures

`providerCurrentTime` means the provider's current Unix time in whole seconds.
A placement is active while:

```text
providerCurrentTime < expiresAt
```

An operation accepted while active completes under its acceptance-time terms
even if expiration occurs during its transfer. At `expiresAt`, a pending
placement becomes expired and may no longer be discovered or recovered.

Conflicting operations on one placement must be serialized. In particular:

```text
recover versus remove
    Exactly one may transition a pending placement.

recover versus expiration
    A recover accepted while pending completes; a later request fails.

renew versus expiration or remove
    The response reflects one definite ordering.

status versus a state change
    The response reports a state that existed at one instant during status.
```

Conditions producing failure without charge include malformed fields, invalid
fixed lengths, unsupported encodings, wrong operation fields, values outside
offering limits, price disagreement, insufficient accepted balance, failed
identity proof, invalid signatures, size or hash mismatch, inactive placement,
wrong sender or recipient, stale expected expiration, and interrupted required
output.

Errors across an unauthorized boundary must not distinguish an unknown
placement from one belonging to another identity. Discovery failure must not
reveal whether any other recipient has messages.

CR2SE has no global adjudicator. A missing message, false status, invalid
receipt, premature deletion, or refused operation may change local trust, but
does not create an automatic credit reversal beyond an explicitly completed
early-release agreement.

    messageId, senderId, recipientId, senderCreatedAt, payloadEncoding,

## 17. Example: redundant delivery

Alice and Bob commonly use Carol, David, Ellen, and Fabian as Messaging
providers.

1. Alice generates one message ID and prepares one signed payload for Bob.
2. For privacy, Alice obtains and verifies Bob's public encryption key and
   encrypts the application message.
3. Alice stores the identical signed message at all four providers with a
   retention period of five years. She records four placement IDs.
4. At any later time before expiration, Bob pays each reachable provider for a
   discovery request. Metadata tells him the sender is Alice and the repeated
   message ID lets him recognize replicas.
5. Bob recovers the copy at Carol, verifies Alice's signature, and decrypts it.
6. Alice later pays the providers for status. Carol returns a signed recovered
   status; the other three report pending.
7. Alice asks David, Ellen, and Fabian for removal quotes. She accepts the
   quotes she considers worthwhile. Each successful removal ends that
   provider's obligation and applies its separately stated early-release
   credits.

Bob could instead recover several replicas. Nothing requires recipients and
senders to coordinate immediately, and no provider is trusted to update another
provider's state.

## 18. Security and interoperability requirements

Providers handle untrusted sizes, arrays, signatures, ciphertext, cursors, and
identifiers. They must validate before allocation, bound discovery work and
output, use overflow-safe arithmetic, stream large payloads in bounded frames,
and durably serialize conflicting state changes.

Paying for store makes unsolicited messaging costly to the sender, but it does
not eliminate spam or make discovery free to the recipient. Providers should
apply sender trust, per-sender and per-recipient placement quotas, and practical
rate limits. Recipient applications should display discovery metadata before
paying to recover an unwanted payload.

Encryption hides payload content but not messaging metadata. Sender signatures
authenticate bytes but do not make a sender trustworthy. Recovery signatures
show protocol authorization and recording but not human receipt. Redundancy
improves availability but does not create consensus or guaranteed delivery.

A version 1 implementation is interoperable only if it:

```text
uses cr2se.messaging version 1 and cr2se.messaging.v1 pricing;
uses exact rational, ceiling, overflow-safe price arithmetic;
authenticates the sender for store and sender-only operations;
authenticates the recipient for discover and recover;
verifies the exact Ed25519 signing inputs defined here;
uses SHA-256 over the exact payload bytes;
uses 32-byte unpredictable message, placement, recovery, and removal IDs;
retains pending payloads durably until recovery, removal, or expiration;
orders and pages discovery results as defined;
implements idempotent recovery and removal accounting;
agrees every price and early-release amount before execution;
does not charge failed operations;
does not require payload encryption or claim plaintext confidentiality;
implements the exact encrypted-payload format when advertising support for it;
preserves placement state across connections and ordinary restart.
```
