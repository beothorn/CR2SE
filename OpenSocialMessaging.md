# CR2SE Open Social Messaging

CR2SE Open Social Messaging is a standard, paid service for reading public,
signed messages directly from the CR2SE identity that publishes them. A
**publisher** is the identity that creates the messages. A **reader** is a
service requester that pays the publisher to return messages. A **feed** is
the set of messages that one publisher currently makes available through this
service.

Public means that any authenticated identity may read the feed under the
publisher's advertised terms. It does not mean anonymous, free, permanent,
accurate, safe, or endorsed by CR2SE.

A reader can connect to several publishers it is interested in, retrieve each
feed, verify every message, and combine the results into one chronological
view. An application can add profiles, following, replies, moderation,
recommendations, notifications, or search. Those are application features;
this service only supplies the signed public-message substrate.

Common terms such as **identity**, **service requester**, **service provider**,
**offering**, **credit issuer**, **check**, and **trust** are defined in the
[CR2SE Glossary](./Glossary.md). Common invocation and charging rules are
defined in [Services](./Services.md), advertisements in [Board](./Board.md),
identity keys and IDs in [Identity](./Identity.md), and transport-independent
invocation in [NodeApi](./NodeApi.md).

---

## 1. Version 1 service

The version 1 Open Social Messaging service is identified by:

```text
service:        cr2se.open-social-messaging
serviceVersion: 1
pricing model:  cr2se.open-social-messaging.v1
```

It has one paid operation:

```text
read
    Return a bounded page of the publisher's public messages.
```

The `read` operation has three selectors:

```text
latest
    Select the newest available messages.

since
    Select available messages at or after one time.

interval
    Select available messages inside one time interval.
```

Creating a message and adding it to the publisher's own feed is called
**publication**. Publication is a local administrative action, not a paid
peer-to-peer operation in version 1. A standalone peer may expose a command,
local API, file watcher, or user interface for publication. A library may
expose a function. These interfaces are implementation-specific, but they
construct the same message representation defined below.

All sizes are measured in bytes. All times are whole Unix seconds. All
protocol integers use the ranges of their declared types; fixed-width integer
arithmetic must never wrap.

## 2. Bytes, integers, text, and time

A **byte string** is an ordered sequence of bytes. Its length is measured in
bytes, not characters.

`uint32` and `uint64` are unsigned 32-bit and unsigned 64-bit integers. In the
canonical encodings below they use network byte order, with the most
significant byte first. `uint32_be(v)` and `uint64_be(v)` denote those exact
four-byte and eight-byte encodings.

A **UTF-8 string** is a byte string containing one valid, shortest-form UTF-8
encoding. Surrogate code points, overlong encodings, and invalid byte
sequences are forbidden. Unicode normalization is not performed. Two strings
compare equal only when their UTF-8 bytes are equal.

For a UTF-8 string `s`, its **length-prefixed encoding** is:

```text
uint64_be(number of UTF-8 bytes in s) || UTF8(s)
```

An **optional string encoding** is:

```text
0x00
    when the value is absent

0x01 || length-prefixed encoding of the value
    when the value is present
```

An absent string differs from a present empty string.

`SHA-256(data)` means the 32 raw bytes produced by SHA-256 over `data`.
Protocol hashes contain those bytes, not their hexadecimal spelling.

**Unix time** is the number of elapsed seconds since
1970-01-01T00:00:00Z, excluding leap seconds. A time in this service is a
`uint64` Unix time. Conversion to a calendar date or local time zone is a user
interface concern.

## 3. Messages

A **message attachment** is an immutable byte string, such as an image, that
is carried with a message and labeled with its media representation. Section 4
defines its exact fields and validation.

A **message** is one immutable, publisher-signed feed entry. It contains text
and may contain message attachments, subsequently called **attachments**. A
message remains the same message when cached, copied between the publisher's
nodes, or returned to different readers.

A **message ID** is a 32-byte value generated by the publisher with a
cryptographically secure random number generator. The publisher must not use
the same message ID for two different messages under the same identity.

The publisher supplies these fields:

```text
messageId:          bytes, exactly 32 bytes
publisherId:        bytes, exactly 32 bytes
publishedAt:        uint64 Unix seconds
body:               UTF-8 string
attachments:        array of attachments
publisherPublicKey: bytes, exactly 32 bytes
publisherSignature: bytes, exactly 64 bytes
```

`publisherId` identifies the feed. It must equal the CR2SE ID of the service
provider and the ID derived from `publisherPublicKey`.

`publishedAt` is the publisher's claimed publication time. It determines feed
ordering, but it is not proof that an external event occurred at that time.

`body` is plain Unicode text. It may contain line breaks and web addresses,
but it is not HTML, Markdown, XML, or executable content. A body may be empty
only when the message has at least one attachment.

`attachments` is ordered and may be empty. Its elements are defined in the
next section. Their order is part of the signed message.

Version 1 messages do not have protocol-level recipients, visibility groups,
replies, reactions, edits, or reshares. An application may encode relationships
using text, links, or a separately specified application format, but must not
change the meaning of the version 1 fields.

## 4. Attachments and images

An **attachment** is one immutable byte string carried by a message. It has:

```text
mediaType: string
fileName:  UTF-8 string, optional
altText:   UTF-8 string, optional
dataSize:  uint64
dataHash:  bytes, exactly 32 bytes
data:      bytes, exactly dataSize bytes
```

`mediaType` labels the representation of `data`. It has length `3 .. 255` and
has exactly this ASCII form:

```text
token "/" token
```

Each `token` contains one or more characters from
`a-z`, `0-9`, `!`, `#`, `$`, `&`, `^`, `_`, `.`, `+`, or `-`. Uppercase,
whitespace, parameters such as `charset=utf-8`, and every other character are
forbidden. Examples include:

```text
image/jpeg
image/png
image/webp
audio/ogg
video/mp4
application/pdf
```

The label follows the familiar Internet media-type form, but a reader must
treat it as untrusted metadata. The bytes, not a file-name extension, determine
what a decoder actually receives.

`fileName`, when present, is a display suggestion. It is not a filesystem path
and must not be used without local sanitization. It must not contain U+0000,
slash U+002F, or reverse solidus U+005C.

`altText`, when present, is a plain-text description of the attachment. It is
particularly useful for an image but has no effect on the attachment bytes.

`dataSize` is the exact number of bytes in `data`. `dataHash` is:

```text
SHA-256(data)
```

Embedding the logical bytes makes a message self-contained and avoids
temporary external links. A transport may stream a large attachment in
bounded frames; streaming does not change `data`, its size, its hash, or its
position in the attachment array.

An application that wants externally hosted media may put its address in the
body. Such linked media is not an attachment, is not covered by `dataHash`, and
may change independently of the message.

## 5. Canonical message bytes and signature

Canonical bytes give independent implementations exactly the same hash and
signature inputs. String constants below are their exact ASCII bytes without
a terminating zero byte.

The **canonical attachment bytes** for one attachment are:

```text
ASCII("CR2SE-OPEN-SOCIAL-ATTACHMENT-V1")
|| length-prefixed encoding of mediaType
|| optional string encoding of fileName
|| optional string encoding of altText
|| uint64_be(dataSize)
|| dataHash
|| data
```

The **canonical message bytes** are:

```text
ASCII("CR2SE-OPEN-SOCIAL-MESSAGE-V1")
|| messageId
|| publisherId
|| uint64_be(publishedAt)
|| length-prefixed encoding of body
|| uint32_be(number of attachments)
|| canonical attachment bytes for attachment 0
|| canonical attachment bytes for attachment 1
|| ...
```

The attachment count must fit in `uint32`. `dataSize` and every string byte
length must match the bytes actually encoded. A constructor must reject any
length or total-size calculation that exceeds its declared range or local
safe processing limits.

The **message hash** is:

```text
messageHash = SHA-256(canonical message bytes)
```

The exact **message signing bytes** are:

```text
ASCII("CR2SE-OPEN-SOCIAL-SIGNATURE-V1") || messageHash
```

`publisherSignature` is the 64-byte Ed25519 signature over the message signing
bytes. Signing the hash permits an implementation to hash attachments while
streaming instead of retaining a second complete copy in memory.

To validate a message, a reader must:

1. derive the CR2SE ID from `publisherPublicKey` and require it to equal
   `publisherId`;
2. require `publisherId` to equal the identity providing the selected feed;
3. validate every field, attachment size, and attachment hash;
4. reconstruct the canonical message bytes and calculate `messageHash`;
5. verify `publisherSignature` over the exact message signing bytes.

A message is invalid if any step fails. A provider-supplied `messageHash` is a
convenience value and must not replace the reader's calculation.

## 6. Availability and feed ownership

The service provider is the publisher. A provider must return only messages
whose `publisherId` equals its own authenticated CR2SE identity and whose
signature verifies under that identity. This rule makes a feed's ownership
unambiguous.

An identity may operate several nodes. Each node may serve all or only some of
the identity's valid messages. CR2SE does not synchronize those nodes. A
publisher that wants identical feeds must arrange replication outside this
service.

The feed is not an archive commitment. A publisher may add or stop serving a
message at any time and does not promise a minimum retention period. A reader
that needs a durable copy may retain a verified message locally or use another
CR2SE service with an explicit retention contract.

A publisher must never replace the bytes associated with an available message
ID. To correct or update content, it publishes a new message and may stop
serving the old one. Version 1 does not define a deletion tombstone, so absence
does not prove that a message never existed.

## 7. Ordering, selectors, and cursors

Messages are ordered from newest to oldest by this pair:

```text
(publishedAt descending, messageId descending)
```

Message IDs use unsigned lexicographic byte order: compare the first unequal
byte as an integer in `0 .. 255`. Descending means the larger value comes
first. The message ID resolves ties when several messages have the same
`publishedAt` value.

A **selector** determines the time range considered by a `read` operation.
Its rules are:

```text
latest
    No lower or upper time bound is supplied.

since
    fromInclusive is required. A message matches when:
        publishedAt >= fromInclusive

interval
    fromInclusive and toExclusive are required, and
    fromInclusive < toExclusive. A message matches when:
        fromInclusive <= publishedAt < toExclusive
```

The half-open interval prevents a message exactly at a boundary from appearing
in both adjacent intervals.

A **cursor** is an optional pair:

```text
beforePublishedAt: uint64 Unix seconds
beforeMessageId:   bytes, exactly 32 bytes
```

Both cursor fields must be absent or both present. A matching message is after
the cursor in the result only when its ordering pair is strictly smaller than
the cursor pair. In other words, a cursor asks for older matching messages and
is exclusive.

The selector is applied first and the cursor second. A caller obtains the next
page by copying the last returned message's `publishedAt` and `messageId` into
the two cursor fields. Newer messages published between page requests do not
reappear on an older page. Messages removed between requests can cause later
pages to contain fewer results; pagination is not a frozen snapshot.

## 8. Pricing and Board offering

Every successful `read` operation costs the exact advertised `readPrice`.
The price does not depend on how many matching messages exist. An empty
successful result is therefore charged. This fixed per-request rule makes the
price knowable before execution and lets credits limit repeated collection.

The pricing field is:

```text
readPrice
    Exact credits charged for one successful read. Range: 1 .. 2^64-1.
```

The offering limits are:

```text
maximumResults
    Largest permitted read limit. Range: 1 .. 2^32-1.

maximumAttachmentsPerMessage
    Largest attachment count in one returned message. Range: 0 .. 2^32-1.

maximumBodyBytes
    Largest UTF-8 body byte length in one returned message.

maximumAttachmentBytes
    Largest dataSize of one returned attachment.

maximumMessageBytes
    Largest canonical message byte length of one returned message.

maximumResponseBytes
    Largest sum of canonical message byte lengths in one read result.
```

Every byte limit is a `uint64` greater than zero, except
`maximumAttachmentsPerMessage`, which may be zero. The provider must ensure:

```text
maximumMessageBytes <= maximumResponseBytes
```

A complete offering has this shape:

```json
{
  "id": "open-social-feed",
  "service": "cr2se.open-social-messaging",
  "serviceVersion": 1,
  "description": "Return bounded pages of this identity's signed public messages.",
  "creditIssuer": "PUBLISHER_ID",
  "pricing": {
    "model": "cr2se.open-social-messaging.v1",
    "readPrice": 1
  },
  "info": {
    "maximumResults": 100,
    "maximumAttachmentsPerMessage": 8,
    "maximumBodyBytes": 65536,
    "maximumAttachmentBytes": 10000000,
    "maximumMessageBytes": 20000000,
    "maximumResponseBytes": 50000000
  },
  "preconditions": [
    "cr2se.identity"
  ]
}
```

The values are illustrative. Every version 1 offering must contain all shown
pricing and `info` fields and the `cr2se.identity` precondition. It must use
`pricing`, not the Board's fixed `price` field. `creditIssuer` may be any
issuer accepted under the common service rules; it need not equal the
publisher.

The limits describe every message that may be returned through that offering.
A publisher must not select an offering for a message that violates any of its
limits. Changing or removing an offering creates no availability promise for
previously published messages.

The exact price and issuer are agreed before the provider begins returning
message bytes. A failed or interrupted operation is not charged.

## 9. Read input

The authenticated reader supplies:

```text
operation:         "read"
selector:          "latest", "since", or "interval"
fromInclusive:     uint64 Unix seconds, conditionally present
toExclusive:       uint64 Unix seconds, conditionally present
beforePublishedAt: uint64 Unix seconds, optional cursor field
beforeMessageId:   bytes, exactly 32 bytes, optional cursor field
limit:             uint32
```

Selector fields are exact:

```text
latest
    forbids fromInclusive and toExclusive

since
    requires fromInclusive and forbids toExclusive

interval
    requires both fromInclusive and toExclusive
```

`limit` must be in `1 .. maximumResults`. The two cursor fields must both be
present or both absent. Unknown selector values fail without charge.

The reader authenticates as a CR2SE identity because invocation and credit
accounting require a requester. Authentication does not grant special access:
every conforming reader is eligible under the same advertised offering and
preconditions.

---

## 10. Read selection and output

After validating the input and agreeing the price, the provider takes the
messages currently available through the selected offering and performs these
steps in order:

1. retain only messages matching the selector;
2. retain only messages strictly after the optional cursor;
3. order the messages as defined in section 7;
4. take consecutive messages from the start until `limit` is reached or the
   next message would make the sum of canonical message byte lengths exceed
   `maximumResponseBytes`.

Because every eligible message is at most `maximumMessageBytes` and that limit
is at most `maximumResponseBytes`, the first matching message always fits. A
provider must not skip a larger matching message to return smaller, older
messages. This makes selection deterministic for one feed state.

Each returned message adds this calculated field:

```text
messageHash: bytes, exactly 32 bytes
```

All other message and attachment fields retain the representations defined in
sections 3 and 4. The successful output is:

```text
operation: "read"
selector:  same selector as the request
messages:  array of complete messages, newest first
more:      bool
price:     uint64 credits
```

`more` is true only when another matching message existed immediately after
the last returned message when selection was performed. If `messages` is
empty, `more` must be false.

The provider must not report success until the complete logical output has
been returned. An interrupted output is a service failure and must not be
charged. A retry is a new invocation with a new price because feed contents
may have changed.

The reader must validate messages before displaying, indexing, or caching them
as authentic. The fact that the transport was connected to the publisher does
not replace signature and hash verification.

## 11. Publication procedure

Publication is local, but independent implementations need the same procedure
to create valid messages. A publisher performs these steps:

1. choose a new random 32-byte `messageId`;
2. set `publisherId` to its own CR2SE ID;
3. choose `publishedAt`, normally its current Unix time;
4. encode `body` as valid UTF-8;
5. for every attachment, choose its metadata, set `dataSize` to the exact byte
   length, and calculate `dataHash`;
6. validate the message against the limits of every offering through which it
   will be served;
7. construct the canonical message bytes and calculate `messageHash`;
8. sign the message signing bytes with the publisher's Ed25519 identity
   private key;
9. durably add the complete immutable message to the feed before announcing
   successful local publication.

The private key must not be sent to another peer. A local publication API
should accept content and use the node's protected identity key internally.
An implementation that imports an already signed message must perform the same
validation as a reader before making it available.

Publication may fail because of an invalid string, invalid media type,
duplicate message ID, excessive size, too many attachments, unavailable
storage, or a signing failure. A failed publication must not expose a partial
message through `read`.

## 12. Verification check

The Open Social Messaging check is local verification of one successful
`read` output. It requires no additional provider message, has no separate
`checkPrice`, and creates no new charge. Exactly one logical check is included
in each successful invocation; an implementation may cache or recompute it.

The check input is the requested publisher identity, the original read input,
the selected offering terms, and the complete returned output. Its outcome is:

```text
pass
    The output metadata matches the request; ordering, selector, cursor,
    result count, and response-size limits are valid; and every returned
    message has matching sizes and hashes plus a valid publisher signature.

fail
    A complete output is available, but at least one property above is false.

inconclusive
    Required request or output data is unavailable, or local resource limits
    prevent complete verification.
```

The reader calculates the outcome. It must not trust a provider-supplied
claim that the output passed.

A pass proves that the returned messages were signed by the publisher identity
and were valid responses to the request, subject to the security of Ed25519
and SHA-256. It cannot prove that the publisher returned every message it has,
that removed messages never existed, that `more` is truthful, or that message
claims and media are accurate or safe.

The result may affect local trust but does not automatically reverse credits
or settle a dispute.

```json
          "more": { "type": "bool", "description": "Claim that another matching message existed immediately after this page." },
          "price": { "type": "uint64", "description": "Exact credits charged for the successful read." }
        } }
      }
    },
    "output": {
      "type": "object",
      "fields": {
        "outcome": { "type": "string", "description": "Requester-computed result: pass, fail, or inconclusive." }
      }
    }
  }
}
```

An implementation may expose functions, iterators, streams, processes, or
language-native records instead of JSON. It must preserve the logical types,
unsigned integer ranges, byte order, UTF-8 rules, canonical encodings,
validation, selection, ordering, price, and observable behavior. In a JSON
binding, `bytes` values require that binding's defined lossless byte encoding;
this specification does not require Base64 on the peer-to-peer wire.

Known selector-specific input fields used with the wrong selector must be
rejected. Unknown fields follow the compatible-extension rule in
`Services.md`.

## 14. Reader algorithm and combined feeds

A minimal reader can maintain a list of publisher identities and, for each
one, an address, accepted offering, and most recently observed ordering pair.
To refresh a combined view it:

1. connects to each selected publisher;
2. retrieves and validates that publisher's Board and service definition;
3. invokes `read` using `latest` or `since` and an application-chosen limit;
4. performs the local verification check;
5. deduplicates by `(publisherId, messageId)`;
6. merges valid messages by `publishedAt`, using publisher ID and message ID as
   deterministic application tie-breakers.

For example, a first request for ten recent messages is:

```text
operation = "read"
selector  = "latest"
limit     = 10
```

A later refresh from Unix time `1788134400` is:

```text
operation     = "read"
selector      = "since"
fromInclusive = 1788134400
limit         = 100
```

The inclusive bound can repeat messages already held by the reader, so the
reader deduplicates them. Inclusion is preferable to losing messages that
share the boundary second.

A bounded historical request is:

```text
operation     = "read"
selector      = "interval"
fromInclusive = 1785542400
toExclusive   = 1788134400
limit         = 100
```

When `more` is true, the reader uses the last returned ordering pair as the
exclusive cursor and pays for another invocation. Different publishers may
use different credit issuers, prices, limits, availability policies, and
clocks. Combining their messages does not combine their ledgers or make their
timestamps equally trustworthy.

## 15. Relationship to RSS and other applications

The message model is inspired by a simple syndication item:

```text
publisherId    identifies the feed owner
messageId      identifies one item
publishedAt    supplies its publication time
body           supplies its text
attachments    supply self-contained media enclosures
```

It is not RSS and does not use XML. XML would add a second canonicalization
problem, while ordinary RSS enclosures usually name external resources rather
than carrying hash-verified bytes. A gateway may expose verified messages as
RSS or import RSS items as newly signed CR2SE messages, but that mapping is an
application decision and does not preserve signatures across formats.

The format is also not email or MIME. It has no private recipient headers,
delivery routing, multipart boundary syntax, or suggestion of confidentiality.
Structured fields plus exact byte lengths are smaller to implement correctly
and work naturally in libraries and streaming standalone peers.

## 16. Failures, concurrency, and clocks

Conditions producing failure without charge include malformed fields, invalid
fixed lengths, invalid UTF-8, invalid selector combinations, invalid cursors,
values outside offering limits, price disagreement, insufficient accepted
credits, failed requester identity proof, unavailable service, and interrupted
required output.

Messages added or removed concurrently with a read must yield one result that
could have been produced from the feed at one instant during selection. The
provider must not return duplicate ordering pairs or internally inconsistent
message bytes.

Ordering uses publisher-claimed `publishedAt`, not reader receipt time. A
publisher clock may be wrong or malicious. A combined-feed application should
retain a local first-seen time and may visually separate messages with implausible
dates. It must not silently alter signed `publishedAt` values.

CR2SE has no global adjudicator. Omitted messages, a false `more` value,
premature removal, invalid content, or refusal to serve may change local trust,
but do not automatically reverse credits.

## 17. Public-content and security requirements

Encryption is not suggested for version 1 message contents. The service is
specifically for public material, and any conforming reader is permitted to
receive the complete body and attachments after satisfying the offering.
Transport protection, encrypted local storage, or a custom service may still
be used without changing this public contract. Implementations that preserve
the interface and all observable rules may choose any internal design.

Signatures provide authorship integrity, not truth or safety. A validly signed
message can contain deception, harassment, illegal material, malware, decoder
exploits, tracking identifiers, or disturbing images. Readers must treat text,
media types, file names, attachment bytes, links, and decoded metadata as
untrusted input.

Implementations must use bounded parsing and streaming, enforce advertised and
local resource limits before allocation, check all arithmetic, and avoid using
untrusted lengths as unchecked allocation sizes. Media should be decoded in a
restricted environment appropriate to the platform. A file name must never be
joined directly to a filesystem path.

Public does not mean freely scrapeable. Identity authentication, nonzero
prices, per-offering limits, and local rate limits can raise the cost of bulk
collection. They cannot prevent an authorized reader from copying or
republishing content it has received. Publishers must assume that every
successfully returned message can persist indefinitely.

The body and attachments are visible to the provider, reader, and any system
where either stores them. Message IDs, sizes, hashes, timestamps, requester
identity, selected publishers, query ranges, and access timing also reveal
information. Applications should not publish private metadata merely because
the primary content is intended to be public.

## 18. Interoperability checklist

A conforming version 1 publisher:

```text
advertises the exact service, version, pricing model, and required limits;
serves only messages signed by its own CR2SE identity;
never changes the bytes associated with one available message ID;
constructs hashes and signatures from the exact canonical bytes;
validates UTF-8, media types, sizes, hashes, and offering limits;
implements latest, since, and half-open interval selection;
orders by publishedAt and messageId from newest to oldest;
uses an exclusive two-field cursor and never skips a matching message to fit;
agrees a fixed nonzero read price before returning content;
does not charge failed or incomplete reads;
supports complete logical bytes even when transport streaming is used.
```

A conforming version 1 reader:

```text
validates the Board offering and retrieved service definition;
preserves full unsigned integer ranges and exact byte strings;
checks publisher identity, canonical hash, signature, and every attachment;
checks selector bounds, cursor exclusion, ordering, count, and size limits;
deduplicates messages using publisher ID together with message ID;
treats all returned content and metadata as untrusted;
does not interpret public availability as permanence, truth, or safety.
```
